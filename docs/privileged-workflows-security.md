# Privileged GitHub Actions security — Phase A2

**NOT READY TO MERGE / NO-GO until the external prerequisites are verified.**
This audit inspects committed workflows, not live GitHub settings or credential
values. The operator reports that A1 is on `main` and `production-results`
allows only `main`, has no reviewers/wait timer, and contains its two secrets.
Those settings have not been independently inspected here. All other environment
rules, secret scopes, branch protections and token privileges remain unverified.

A2 changes three database workflows, adds local security regression tests, and
documents configuration and cutover. It does not change application rules,
migrations, CI pipelines, import-results.yml, Supabase Cron, Vercel configuration
or developer setup. Do not run hosted commands or workflow verification as part
of this local preparation. The operator steps below require separate approval.

## Workflow audit and resulting behavior

All six workflows use GitHub-hosted Ubuntu runners and `contents: read` for
`GITHUB_TOKEN`. None uses `pull_request_target`, `workflow_run`, reusable
workflows, explicit arbitrary checkout refs or self-hosted runners.

| Workflow | Triggers | Ref admitted after A2 | Environment / access | Explicit GitHub secrets |
| --- | --- | --- | --- | --- |
| [database-deploy-production.yml](../.github/workflows/database-deploy-production.yml) | Push to `main`, only migration paths; manual dispatch | Canonical repository, `refs/heads/main`, push/dispatch; existing `DATABASE_MIGRATIONS_ENABLED == 'true'` | `production`, referring to existing **Production**; applies production migrations | `SUPABASE_ACCESS_TOKEN`, `SUPABASE_DB_PASSWORD`, `SUPABASE_PROJECT_ID` |
| [database-deploy-staging.yml](../.github/workflows/database-deploy-staging.yml) | Push to `develop`, only migration paths; manual dispatch | Canonical repository, `refs/heads/develop`, push/dispatch; same enable flag | `staging`; applies staging migrations | Same three names, with staging-specific credentials |
| [database-status.yml](../.github/workflows/database-status.yml) | Manual dispatch; staging/production input | Canonical repository, dispatch only; production on `refs/heads/main`, staging on `refs/heads/develop` | Selected `production`/`staging`; hosted schema/history reads and push preview | Same three names, selected environment's credentials |
| [import-results.yml](../.github/workflows/import-results.yml) | Nightly 00:07 Stockholm schedule; manual or Cron workflow dispatch | Existing A1 guard: canonical repository, `refs/heads/main`, schedule/dispatch | `production-results`; production fixture/result writes, scoring, gameweek completion | `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` |
| [pull-request-ci.yml](../.github/workflows/pull-request-ci.yml) | PR into `develop`/`main`; manual dispatch | PR merge refs or chosen dispatch ref; intentionally validates branch code | None; disposable local Supabase, build/unit/functional/browser checks | None; local keys are generated by the runner |
| [database-migrations-ci.yml](../.github/workflows/database-migrations-ci.yml) | PR on migration/config/database-workflow paths, without target-branch filter; manual dispatch | PR merge refs or chosen dispatch ref | None; local rebuild, dispatch-window SQL, lint/history | None |

Canonical repository means `BE4M3R/fantasy-pingisligan`. Production YAML retains
its existing lowercase reference and status input: GitHub environment names
are case insensitive, so `production` binds **Production**. Keep the binding
unchanged. See [GitHub environment configuration](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments).
No tracked workflow uses **Preview**; integration-created deployments and its
contents still need an administrator's metadata audit.

Before A2, both deploy jobs guarded only the enable flag. Push filters did not
restrict manual dispatch refs. Status had no guard on ref or selected target.
If the environments allow feature refs, branch-controlled code can obtain
their credentials. Even with environment restrictions, repository/organization
credentials remain accessible to eligible branch workflows without binding an
environment. Fork PR secret withholding does not protect same-repository branch
runs. Guards are editable by branch code; external restrictions and broad-secret
cleanup establish the boundary.

Status is an inspection operation but uses the same privileged token/password
as deployments. A dry-run label does not make it offline or limit the supplied
credentials. A2 preserves schema diff, migration history, baseline verification,
dry-run/apply order, concurrency, timeouts, filenames and CLI version. It removes
staging's CLI `--debug` flag to reduce logging exposure; no actual credential
leak has been established by this audit.

The command audit also corrects status's existing diff capture: CLI 2.116.0
uses `--output` only in explicit `--from`/`--to` mode. A normal `--linked`
diff prints SQL to stdout, so the previous invocation could leave
`schema-diff.sql` absent and silently pass the file-size check despite drift.
Status now redirects stdout to that file; SQL differences fail the existing
check, and a failed CLI command stops the step. The diff engine, schema filter
and database target are unchanged. See the [pinned CLI diff handler](https://github.com/supabase/cli/blob/v2.116.0/apps/cli/src/legacy/commands/db/diff/diff.handler.ts).

Manual runs on the wrong branch/target, tags named `main` or `develop`, PR refs,
forks and unsupported events fail the new guards before checkout. A modified
branch workflow must additionally be denied by the environment's branch rule.
Reruns preserve the original ref, commit and original actor privileges, rather
than picking up this new guard. Old runs therefore require review and cleanup;
do not rerun pre-A2 database jobs or pre-A1 import jobs. See [GitHub rerun behavior](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/re-run-workflows-and-jobs).

## Credential-consumer audit

| Broad repository secret | Consumers in this checkout | Required restricted location | Removal dependency |
| --- | --- | --- | --- |
| `SUPABASE_ACCESS_TOKEN` | Both database deploy workflows and database status | Environment secret in **Production** and **staging**, preferably different project-scoped tokens | Verify both replacements, status and normal deployments; inventory other token holders before revocation |
| `SUPABASE_SERVICE_ROLE_KEY` | Only import-results.yml | **production-results** only, already configured according to operator | Successful natural nightly and due poll using A1; finish copy/consumer audit |
| `SUPABASE_URL` | Only import-results.yml | **production-results**, already configured according to operator | Same results verification; remove together with broad service-role copy |

`SUPABASE_DB_PASSWORD` and `SUPABASE_PROJECT_ID` are also referenced by all
three database workflows. Their live scopes were not supplied. Check them by
name and keep each exclusively in its correct database environment; remove
broad copies if found. A project ID or URL does not authorize a database request
alone, but its pairing must still be correct. No importer, local test runner or
application automatically downloads GitHub Actions secrets. Local scripts use
operator-managed environment files/local generated keys; Vercel settings are
independent consumers if the underlying credentials are shared.

The name `SUPABASE_ACCESS_TOKEN` does not reveal its type or authority. A classic
Supabase PAT inherits the owner's account privileges across projects, potentially
including project management and API key retrieval. Moving it into a GitHub
environment restricts delivery, not its management authority. Scoped PATs can
limit project and permissions. The existing `supabase link` needs **Project
Settings**, **API Keys** and **API Key Secrets**, each **Read**. The supplied
database password still permits database commands independently of PAT scopes.
Use different single-project PATs for production and staging, and verify their
compatibility with pinned CLI 2.116.0 before retiring the old token. These are
documented capabilities, not findings about this repository's actual token.
See [Supabase PAT permissions and CLI usage](https://supabase.com/docs/guides/platform/personal-access-tokens#use-a-scoped-personal-access-token-with-the-supabase-cli).

Separate classic PATs owned by the same broadly privileged account do not
isolate projects. If scoped tokens are unavailable, document an
alternative using identities with only the necessary project access; do not
claim staging/production credential isolation with a cross-project classic PAT.
Do not put migration tokens/passwords in `production-results` or production
credentials in staging/Preview. The existing production Vault dispatch token is
an independent GitHub credential and stays unchanged.

## Exact manual GitHub configuration

An authorized administrator must perform and record these steps using metadata
only. Do not extract existing secret values from GitHub, logs or workflow runs,
or paste values into reports, terminals, screenshots or the repository. Provision
credentials directly through the trusted operator's secret-management process.

1. Open **BE4M3R/fantasy-pingisligan → Settings → Environments**. Verify repository
   visibility/plan supports environment secrets and selected deployment branch
   rules. Check the current default branch is `main`. Open the existing entries;
   do not delete/recreate or rename **Production**, **staging**, **Preview** or
   **production-results**. Record rules, secret names and reviewer policy.
2. In **Production → Deployment branches and tags**, choose **Selected branches
   and tags**. Remove all existing rules except a rule with **Ref type: Branch**,
   **Name pattern: main**; add that exact rule if absent. Add no tags/wildcards,
   PR refs or develop rule. Do not use **Protected branches only** (it can admit
   other protected branches) or **No restriction**.
3. In **staging**, apply the same procedure with the only Branch pattern
   **develop**. No main, feature, PR or tag rule.
4. In **production-results**, verify the only rule is Branch **main**. Preserve
   **Required reviewers disabled**, **Wait timer disabled** and no custom approval
   gates, so nightly and Cron-dispatched imports stay unattended.
5. For **Production**, the recommendation is one independent trusted deployment
   reviewer. If supported by the repository's visibility/plan, select **Required
   reviewers**, add the reviewer/team, enable **Prevent self-review**, save, and
   deselect **Allow administrators to bypass configured protection rules**.
   Leave the wait timer disabled. This gates all jobs using Production, including
   status and any integration deployments. Inspect existing consumers first and
   record acceptance of that behavior change. If unavailable, record reliance
   on independently reviewed branch promotion instead; do not silently mark a
   reviewer gate verified. Keep any stronger existing approved protections.
6. For **staging**, leave reviewers/wait timer disabled for automatic deployment
   after reviewed develop merges; preserve any intentional existing reviewer
   policy and record its impact before changing it. Disable administrator bypass
   where available. Never apply the production migration approval gate to
   `production-results`.
7. In **Production → Environment secrets**, ensure exactly the required database
   names exist for that project: **SUPABASE_ACCESS_TOKEN**, **SUPABASE_DB_PASSWORD**,
   **SUPABASE_PROJECT_ID**. Repeat in **staging** with its own project credentials.
   In **production-results**, verify **SUPABASE_URL** and
   **SUPABASE_SERVICE_ROLE_KEY** exist. Audit extra privileged names rather than
   deleting an integration's unrelated secrets. Environment secrets override
   same-named repository secrets; a missing environment secret can still fall
   back to the repository copy, so metadata verification is essential.
8. Inspect **Preview** without changing its deployment policy. No tracked Actions
   workflow needs it. Identify integration consumers and secret names, verify
   that no production/staging PAT, database password or service-role key is
   reachable from feature code there. If found, migrate that consumer to a
   suitable restricted environment or remove the credential after review. Keep
   Preview's existing purpose; a main-only rule would break branch previews.
9. Open **Settings → Branches → Branch protection rules** and edit/create exact
   rules for **main** and **develop** (or enforce equivalent active rulesets).
   Enable **Require a pull request before merging**, at least **1 approval**,
   **Dismiss stale pull request approvals when new commits are pushed**, and
   **Require approval of the most recent reviewable push**. Enable **Require
   status checks to pass before merging** and **Require branches to be up to
   date**. Require the existing **code-and-unit** and **functional-and-browser**
   checks, selecting GitHub Actions as their expected source when offered.
   Disable force pushes/deletions and direct-push or PR bypass allowances;
   enable **Do not allow bypassing the above settings** for admins/custom roles.
   Preserve stronger existing rules. A trusted independent reviewer must be
   available; do not grant everyday developer/AI identities administrative or
   bypass access. Review workflow, script, package/install-hook and migration
   changes before they enter these credential-bearing branches.
10. Keep feature → develop → main promotion; require operational review that the
    promoted develop commit passed staging. The existing database **validate**
    check is path-filtered: retain it for matching PRs, but do not make it an
    unconditional required check or unrelated PRs may wait forever. No CI changes
    are needed. Review **Settings → Actions → General → Workflow permissions**:
    use read repository contents permission by default and leave PR creation
    approval permission disabled unless another audited consumer requires it.
11. In **Settings → Secrets and variables → Actions → Secrets**, inventory names
    and scopes of repository secrets and organization secrets available here,
    including equivalent credentials stored under aliases. Check inherited
    organization availability with its administrator. Under **Variables**,
    preserve the current location/value of **DATABASE_MIGRATIONS_ENABLED**;
    do not move it into an environment, since the existing job guard evaluates
    before the environment starts. Record extra integration/Vercel consumers
    of the underlying credentials before any token revocation.

Environment enforcement applies before secrets are available, but authorizes a
branch, not one workflow. Trusted main/develop code can request any environment
that permits that ref. See [GitHub environment setup and feature availability](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments),
[branch-protection configuration](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/managing-a-branch-protection-rule)
and [path-filtered required checks](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks).

## Secret migration and removal order

1. Verify environment/branch protections and complete the name/scope/consumer
   inventory first. Record the current reviewed commits and credential ownership,
   expiry and project permissions without values. Keep the temporary overlap
   controlled: broad credentials still allow branch code to bypass the boundary.
2. Provision the database credentials in **staging** and **Production** under
   their unchanged names. Prefer new project-scoped PATs using only the three
   Read scopes needed for link. This audit does not generate or handle tokens.
   Confirm staging cannot manage production. Database passwords remain privileged.
3. After separate authorization, verify replacements with **Check database
   migration status**: select branch **develop** with input **staging**, then
   branch **main** with input **production**. Approve Production if configured.
   These access hosted databases; do not perform them during Phase A2 preparation.
   Watch normal, already-approved migration deployments on both targets; do not
   create a migration or dispatch an apply job merely to test a secret.
4. After database consumers and replacements are verified, delete the repository
   **SUPABASE_ACCESS_TOKEN** in **Settings → Secrets and variables → Actions**.
   Remove this repository's access to equivalent organization-secret copies.
   Remove broad DB password/project-ID copies, if present, only after their
   environment replacements and consumers are verified. This can precede results
   cleanup: import-results.yml does not use the management token.
5. Follow the [A1 natural-run observation](production-results-security.md#safe-cutover-sequence):
   confirm a successful automatic nightly import and a naturally due Cron poll
   use `production-results`, start unattended and preserve results/scoring/
   completion. Wait for a real fixture window if necessary. Then remove repository
   **SUPABASE_SERVICE_ROLE_KEY** and **SUPABASE_URL** together and any equivalent
   organization availability. Do not remove environment copies. No other tracked
   workflow needs these two broad secrets.
6. Review pending, queued and active jobs before/after deletions. Let legitimate
   active operations finish; cancel obsolete or untrusted queued/pending runs.
   Repository/organization secrets are captured at queue time, environment secrets
   at job start. Deleting a secret does not revoke a captured credential. Do not
   rerun legacy revisions even on main/develop: they may run outdated code with
   current environment secrets. See [secret precedence and read timing](https://docs.github.com/en/actions/reference/security/secrets).
7. After all other users of the old PAT are migrated, revoke it in the Supabase
   operator's token settings. Deleting GitHub's copy alone does not revoke it.
   Inventory shared service-role/password users before any rotation; schedule
   coordinated rotation separately if exposure is suspected or revocation is
   needed. Do not rotate the project's signing key or break Vercel as incidental
   cleanup. Confirm another natural results run and new trusted database status/
   normal deployment work after broad-secret removal.

## Verification, impact and rollback

Local `npm run check` runs lint, typecheck and all unit tests, including the
new guards' repository/ref/event/enable-flag and status-target matrices. It
also parses all workflow YAML and checks the known Supabase credential consumers,
PR validation's lack of environment bindings, and the existing A1 tests.
These tests do not emulate GitHub environment enforcement, reviewer gates, rerun
authorization or Supabase token permissions. Record actual local results in the
handoff; no hosted workflow or database execution belongs to this phase.

The YAML changes keep automatic migration pushes and correct-branch manual runs.
Wrong-branch status/deployment attempts are skipped. Migration paths, flag,
baseline, previews/apply, CI/PR checks and environment names stay intact. An
optional Production reviewer introduces an intentional approval pause for
migrations/status and existing Production integration jobs, not results imports.
Developer commands, Node dependencies and environment files are unchanged;
tests use Node and the already installed YAML parser across Windows, macOS,
Linux and WSL2, without a new shell tool or platform requirement.

Before recommending merge, the administrator must record:

- [ ] Supported environment restrictions, exact branch-only rules and audited Preview access.
- [ ] Required environment secret names and project-specific token permissions verified.
- [ ] Main/develop PR reviews/checks and admin/bypass restrictions enforced.
- [ ] Production reviewer decision and effects on integration/status jobs accepted.
- [ ] Consumer inventory and controlled cleanup plan accepted; queued legacy runs accounted for.
- [ ] Local checks and credential-free PR CI pass for the reviewed change.

After authorized promotion, record successful trusted database status/deployments,
natural results runs, broad-secret removal and old-PAT retirement separately.
Merge approval is not proof that credential isolation is complete. If a negative
enforcement test is desired, use a separately authorized secret-free canary with
synthetic data and matching policies; never execute modified feature workflows
against real privileged environments to prove denial.

For rollback, correct environment secrets/policies in place while retaining exact
branch restrictions. Recover the existing migration enable flag only at its
current scope if it was accidentally changed. For code issues, prepare a reviewed
rollback through feature → develop → main that retains A2 guards and environment
bindings; do not rerun old workflow revisions. Do not restore broad secrets,
widen branch policies, reset a hosted database or revert deployed migrations.
Keep the A1 results workflow, dispatch inputs, Cron credential and unattended
environment unchanged. Failed migration recovery uses the existing reviewed
forward-migration process; this phase creates no migration.

**GO for merge** needs passing local/PR checks and verified external prerequisites
with an accepted cutover plan. **GO for completed isolation** additionally needs
successful post-cutover operation, broad-copy removal and legacy-run cleanup.
Unverified settings mean **NO-GO / NOT READY TO MERGE**. Stop after this local A2
handoff for review; do not promote, execute workflows or change hosted settings.
